# The 150-step Git and GitHub command guide

> Generated by `pnpm docs:generate` from `modules/curriculum/data/guide.ts`. Do not edit by hand.

## 1. Setup

*Beginner*. Install check, identity, defaults and SSH access to GitHub.

### Step 1: Check Git is installed

```bash
git --version
```

Prints the installed Git version. If the command is not found, install Git first.

### Step 2: Set your name

```bash
git config --global user.name "Your Name"
```

Every commit records an author name. --global applies to all your repositories.

### Step 3: Set your email

```bash
git config --global user.email "you@example.com"
```

GitHub matches this email to your account. A GitHub noreply address keeps your real one private.

### Step 4: Default branch name

```bash
git config --global init.defaultBranch main
```

New repositories start on main instead of the older default name.

### Step 5: Choose your editor

```bash
git config --global core.editor "code --wait"
```

Git opens this editor for commit messages and interactive rebase. The example uses VS Code.

### Step 6: Auto-track on first push

```bash
git config --global push.autoSetupRemote true
```

The first git push on a new branch sets its upstream automatically.

### Step 7: Safe pull behaviour

```bash
git config --global pull.ff only
```

git pull only fast-forwards. If histories diverged it stops instead of creating a surprise merge commit.

> **Tip:** pull.rebase true is a valid alternative. Both are opinions; pick one deliberately.

### Step 8: Review all settings

```bash
git config --global --list --show-origin
```

Shows every global setting and the file it came from.

### Step 9: Create an SSH key

```bash
ssh-keygen -t ed25519 -C "you@example.com"
```

Creates a key pair in ~/.ssh. Add a passphrase.

> **Warning:** Never share or paste the private key (id_ed25519). Only the .pub file goes to GitHub.

### Step 10: Test the SSH connection

```bash
ssh -T git@github.com
```

Confirms GitHub accepts your key.

Expected output: `Hi <username>! You've successfully authenticated, but GitHub does not provide shell access.`

## 2. Your first repository

*Beginner*. Create a repo, stage, commit and read your first history.

### Step 11: Create a repository

```bash
git init
```

Turns the current folder into a Git repository by creating the hidden .git directory.

### Step 12: See the state

```bash
git status
```

Shows which files are untracked, modified or staged. Run it constantly.

### Step 13: Create a file

```bash
echo "# My project" > README.md
```

A plain shell command (not Git) that creates the first file to track.

### Step 14: Stage the file

```bash
git add README.md
```

Moves the file into the staging area, the draft of your next commit.

### Step 15: Short status

```bash
git status -s
```

A compact status: the left column is the staging area, the right is the working tree.

### Step 16: Make your first commit

```bash
git commit -m "docs: add README"
```

Saves a snapshot of everything staged. Use Conventional Commits: type: short description.

### Step 17: Read the history

```bash
git log --oneline
```

One line per commit: short hash and message.

### Step 18: Inspect a commit

```bash
git show HEAD
```

Shows the latest commit: metadata plus the exact change.

### Step 19: See unstaged changes

```bash
git diff
```

After editing a file, shows what changed but is not staged yet.

### Step 20: See staged changes

```bash
git diff --staged
```

Shows exactly what the next commit will contain. Review it before every commit.

## 3. The daily loop

*Beginner*. Stage precisely, fix mistakes before they spread, keep history tidy.

### Step 21: Stage by hunk

```bash
git add -p
```

Walks through each change and lets you stage only some of them. Keeps commits focused.

### Step 22: Stage everything

```bash
git add .
```

Stages all changes in the current directory.

> **Tip:** Run git status first. Blind git add . is how secrets and junk get committed.

### Step 23: Discard a file change

```bash
git restore README.md
```

Restores the file to the last committed (or staged) version.

> **Warning:** Uncommitted edits to that file are lost permanently.

### Step 24: Unstage a file

```bash
git restore --staged README.md
```

Removes the file from the staging area but keeps your edits.

### Step 25: Fix the last commit

```bash
git commit --amend --no-edit
```

Adds staged changes to the previous commit, keeping its message.

> **Warning:** Rewrites history. Only do this before the commit is pushed.

### Step 26: Commit tracked changes

```bash
git commit -am "fix: correct typo"
```

Stages and commits all modified tracked files. New files are not included.

### Step 27: Delete a tracked file

```bash
git rm old.txt
```

Deletes the file and stages the deletion in one step.

### Step 28: Rename a file

```bash
git mv a.txt b.txt
```

Renames the file and stages the rename.

### Step 29: Preview a clean

```bash
git clean -nd
```

Dry run: lists untracked files and folders that git clean would delete.

> **Tip:** Always dry-run first. Only then consider git clean -fd.

### Step 30: Draw the history

```bash
git log --oneline --graph --all
```

ASCII graph of every branch. The best single command for understanding a repo.

## 4. Ignore and inspect

*Beginner*. Keep junk out of Git and learn to read history like a detective.

### Step 31: Ignore a folder

```bash
echo "node_modules/" >> .gitignore
```

Tells Git never to track node_modules. Commit the .gitignore file itself.

### Step 32: Why is it ignored?

```bash
git check-ignore -v node_modules
```

Shows which .gitignore rule matches a path.

### Step 33: Stop tracking a file

```bash
git rm --cached secret.txt
```

Removes the file from Git but keeps it on disk. Needed when a file was committed before being ignored.

> **Warning:** It stays in old commits. A leaked secret must be rotated, not just untracked.

### Step 34: List tracked files

```bash
git ls-files
```

Shows every file Git currently tracks.

### Step 35: History of one file

```bash
git log -p -- app/page.tsx
```

Every commit that touched the file, with its diff.

### Step 36: Commit sizes

```bash
git log --stat
```

Lists files changed and line counts per commit.

### Step 37: Who wrote this line?

```bash
git blame app/page.tsx
```

Annotates each line with its last commit. Use it for context, not blame.

### Step 38: Filter by author

```bash
git log --author="Name"
```

Shows only commits by matching authors.

### Step 39: Filter by date

```bash
git log --since="2 weeks ago"
```

Shows commits from a relative or absolute date onwards.

### Step 40: Commits per person

```bash
git shortlog -sn
```

Counts commits per author, most active first.

## 5. Branching and merging

*Beginner*. One branch per change; merge it back safely.

### Step 41: List branches

```bash
git branch
```

Lists local branches. The current one has an asterisk.

### Step 42: Branches with upstreams

```bash
git branch -vv
```

Shows each branch's last commit and its upstream, including ahead/behind counts.

### Step 43: Create and switch

```bash
git switch -c feature/login
```

Creates a new branch at the current commit and switches to it.

### Step 44: Switch branch

```bash
git switch main
```

Moves HEAD and your files to another branch. Commit or stash changes first.

### Step 45: Jump back

```bash
git switch -
```

Switches to the previously checked-out branch.

### Step 46: Rename a branch

```bash
git branch -m old-name new-name
```

Renames a local branch.

### Step 47: Merge a branch

```bash
git merge feature/login
```

Brings the branch's commits into the current branch. Fast-forwards when possible.

### Step 48: Force a merge commit

```bash
git merge --no-ff feature/login
```

Always creates a merge commit so the branch stays visible in history.

> **Tip:** Whether to prefer --no-ff is a team convention, not a rule.

### Step 49: Delete a merged branch

```bash
git branch -d feature/login
```

Deletes the branch only if it is fully merged. Safe.

> **Warning:** -D forces deletion even if unmerged and can lose work.

### Step 50: Which branches are merged?

```bash
git branch --merged
```

Lists branches already merged into the current one: candidates for cleanup.

## 6. GitHub and remotes

*Intermediate*. Connect to GitHub, push, fetch, pull and clone.

### Step 51: Create the GitHub repo

```bash
gh repo create my-repo --private --source=. --remote=origin --push
```

Creates a private GitHub repository from the current folder, adds origin and pushes.

### Step 52: Or add a remote manually

```bash
git remote add origin git@github.com:USER/REPO.git
```

Registers a remote named origin. Replace USER/REPO with yours.

### Step 53: List remotes

```bash
git remote -v
```

Shows each remote and its fetch/push URLs.

### Step 54: First push

```bash
git push -u origin main
```

Uploads main to origin and records it as upstream so later git push and git pull just work.

### Step 55: Fetch updates

```bash
git fetch
```

Downloads new commits from the remote without changing your branches. Safe to run anytime.

### Step 56: What is new upstream?

```bash
git log main..origin/main --oneline
```

Lists commits on origin/main that you do not have yet.

### Step 57: Pull

```bash
git pull
```

Fetch plus integrate. With pull.ff only it refuses to create surprise merges.

### Step 58: Clone a repository

```bash
git clone git@github.com:USER/REPO.git
```

Copies a remote repository with its full history and sets origin.

### Step 59: Switch HTTPS to SSH

```bash
git remote set-url origin git@github.com:USER/REPO.git
```

Changes the URL of an existing remote.

### Step 60: Delete a remote branch

```bash
git push origin --delete feature/login
```

Removes the branch from GitHub. Usually done after the pull request is merged.

## 7. Pull requests

*Intermediate*. Ship every change through a reviewed pull request.

### Step 61: Start from fresh main

```bash
git switch main && git pull
```

Always branch from an up-to-date main.

### Step 62: Create the feature branch

```bash
git switch -c feature/task-filter
```

One branch per change. Name it by purpose.

### Step 63: Push the branch

```bash
git push -u origin HEAD
```

Pushes the current branch and sets upstream. HEAD means the branch you are on.

### Step 64: Open a pull request

```bash
gh pr create --fill
```

Creates the PR using your commit message as title and body. Omit --fill to be prompted.

### Step 65: List open PRs

```bash
gh pr list
```

Shows open pull requests in the repository.

### Step 66: Open the PR in the browser

```bash
gh pr view --web
```

Opens the PR page so you can review the Files changed tab.

### Step 67: Watch the checks

```bash
gh pr checks
```

Shows the status of CI checks on the PR.

### Step 68: Read the diff

```bash
gh pr diff
```

Prints the pull request diff in the terminal.

### Step 69: Check out someone's PR

```bash
gh pr checkout 12
```

Fetches PR #12 and switches to its branch for local testing.

### Step 70: Squash-merge and clean up

```bash
gh pr merge 12 --squash --delete-branch
```

Merges PR #12 as one commit and deletes the branch.

> **Tip:** After merging: git switch main && git pull to update your local main.

## 8. Conflicts and undo

*Intermediate*. Resolve conflicts calmly and undo any mistake.

### Step 71: A merge conflicts

```bash
git merge other-branch
```

When both branches changed the same lines, Git stops and marks the conflict.

### Step 72: See conflicted files

```bash
git status
```

Files marked both modified need your decision.

### Step 73: List only conflicts

```bash
git diff --name-only --diff-filter=U
```

Prints just the unmerged paths.

### Step 74: Mark as resolved

```bash
git add app/page.tsx
```

After editing out the <<<<<<<, =======, >>>>>>> markers, stage the file. Then git commit.

> **Tip:** Run your build after resolving. A resolved conflict can still be broken code.

### Step 75: Abort the merge

```bash
git merge --abort
```

Cancels the merge and returns to the state before it started.

### Step 76: Undo a commit, keep staged

```bash
git reset --soft HEAD~1
```

Moves the branch back one commit; changes stay staged.

> **Warning:** Rewrites history. Do not use on commits already pushed.

### Step 77: Undo a commit, keep files

```bash
git reset HEAD~1
```

Default (mixed) reset: commit undone, changes kept but unstaged.

### Step 78: Undo a pushed commit safely

```bash
git revert abc1234
```

Creates a new commit that reverses abc1234. Safe for shared history.

### Step 79: The safety net

```bash
git reflog
```

Lists where HEAD has been, including commits you thought were lost.

### Step 80: Return to a reflog entry

```bash
git reset --hard abc1234
```

Moves the branch and your files to that commit.

> **Warning:** --hard discards uncommitted work. Practice in a sandbox repository first.

## 9. Advanced history

*Advanced*. Stash, rebase, cherry-pick, bisect and worktrees.

### Step 81: Shelve work

```bash
git stash push -m "wip: dropdown"
```

Saves tracked changes aside and cleans the working tree. Add -u to include untracked files.

### Step 82: List stashes

```bash
git stash list
```

Shows every stash entry.

### Step 83: Restore a stash

```bash
git stash pop
```

Re-applies the latest stash and removes it from the list.

### Step 84: Rebase onto main

```bash
git rebase main
```

Replays your branch's commits on top of the latest main for a linear history.

> **Warning:** Never rebase commits that others already have.

### Step 85: Tidy commits

```bash
git rebase -i HEAD~3
```

Interactive rebase: reorder, reword, squash or drop the last three commits.

### Step 86: Cancel a rebase

```bash
git rebase --abort
```

Stops the rebase and restores the original branch.

### Step 87: Copy one commit

```bash
git cherry-pick abc1234
```

Applies the change from one commit onto your current branch as a new commit.

### Step 88: Force push safely

```bash
git push --force-with-lease
```

After a rebase, overwrites your remote branch only if nobody else pushed to it.

> **Warning:** Never force push to main. Prefer --force-with-lease over --force.

### Step 89: Hunt a bug

```bash
git bisect start
```

Begins a binary search for the commit that introduced a bug. Then use git bisect bad / good, and git bisect reset when done.

### Step 90: Second working folder

```bash
git worktree add ../hotfix -b hotfix/login
```

Checks out a new branch in a separate folder so you can work on two branches at once.

## 10. Releases, CI and security

*Pro Max*. Tags, releases, Actions, hooks, secrets and forks.

### Step 91: Tag a release

```bash
git tag -a v1.0.0 -m "Release 1.0.0"
```

Creates an annotated tag marking this exact commit as version 1.0.0.

### Step 92: Push the tag

```bash
git push origin v1.0.0
```

Tags are not pushed by a normal git push.

### Step 93: Publish a GitHub release

```bash
gh release create v1.0.0 --generate-notes
```

Creates the release and auto-generates notes from merged pull requests.

### Step 94: Track work with an issue

```bash
gh issue create --title "Add done checkbox" --label enhancement
```

Opens an issue. Reference it in a PR with Closes #1 to auto-close it on merge.

### Step 95: List CI runs

```bash
gh run list
```

Shows recent GitHub Actions workflow runs.

### Step 96: Read a failing run

```bash
gh run view --log-failed
```

Prints the logs of failed steps so you can find the cause fast.

### Step 97: Install Git hooks

```bash
pnpm exec husky init
```

Adds the prepare script and a .husky/pre-commit hook. Then replace its content with pnpm exec lint-staged.

> **Tip:** Do not run husky with --help; it treats the argument as a hooks folder and changes core.hooksPath.

### Step 98: Find when code changed

```bash
git log -S"useState" -- app/
```

Pickaxe search: commits that added or removed that exact string.

### Step 99: Fork and clone

```bash
gh repo fork OWNER/REPO --clone
```

Forks an open-source repository to your account and clones it. origin is your fork.

### Step 100: Sync your fork

```bash
git fetch upstream && git merge --ff-only upstream/main
```

Brings the original repository's changes into your main. Add upstream first with git remote add upstream <url>.

## 11. Organization governance

*Enterprise*. Inventory organizations, repositories, teams, owners and repository policies.

### Step 101: List organizations

### Step 103: List organization repositories

```bash

```

### Step 104: List organization teams

### Step 105: Inspect repository settings

```bash
gh repo view OWNER/REPO
```

Reviews visibility, description and repository metadata.

### Step 106: Change repository settings

```bash
gh repo edit OWNER/REPO --enable-issues --enable-discussions
```

Updates explicitly named repository capabilities.

### Step 107: List repository owners

```bash
gh api repos/OWNER/REPO/collaborators
```

Returns direct collaborators; team permissions may be inherited and need separate review.

### Step 108: Read CODEOWNERS

```bash
gh api repos/OWNER/REPO/contents/.github/CODEOWNERS
```

Reads ownership policy so review rules can be audited.

### Step 109: List repository topics

```bash
gh api repos/OWNER/REPO/topics --header Accept=application/vnd.github+json
```

Reviews classification topics used for discovery and inventory.

### Step 110: Archive a repository

```bash
gh repo archive OWNER/REPO
```

Makes a repository read-only after confirming no service or team still depends on it.

> **Warning:** Archive is a governance change. Verify the decommission plan and rollback owner first.

### Step 129: List ruleset history

Retrieves organization audit events for review or evidence collection.

### Step 142: List secret scanning alerts

```bash
gh api orgs/ORG/secret-scanning/alerts
```

### Step 143: List code scanning alerts

```bash
gh api repos/OWNER/REPO/code-scanning/alerts
```

Reviews static-analysis findings and their remediation status.

### Step 144: Read the dependency SBOM

```bash
gh api repos/OWNER/REPO/dependency-graph/sbom
```

Exports repository dependency data as an SPDX-compatible SBOM.

### Step 145: List Dependabot alerts

Inventories vulnerable dependencies and whether fixes are available.

### Step 147: Mirror a repository


### Step 150: Open the enterprise baseline

```bash

```

Starts a repeatable baseline review of Actions policy and audit evidence.
